# Java数据结构学习笔记（第二篇）：时间和空间复杂度

> 上一篇结尾留了一句话：衡量算法好坏，要看时间复杂度和空间复杂度。这篇就把这两个词拆开——怎么数、怎么化简、怎么比较，以及为什么两行递归代码能把电脑算到卡住。

---

## 一、先看两行代码的代价

下面这段求斐波那契数列的代码，短得不能再短：

```java
static long fib(int n) {
    if (n < 2) {
        return n;
    }
    return fib(n - 1) + fib(n - 2);
}
```

逻辑很干净：前两项是 0 和 1，后面每一项等于前两项之和。看起来人畜无害。

但它真正跑起来是这样的：

```
递归 fib(10) = 55，调用 177 次
递归 fib(20) = 6765，调用 21891 次
递归 fib(30) = 832040，调用 2692537 次
```

n 从 10 涨到 30，只多了 20，调用次数从一百多涨到两百六十多万。如果继续往上加，n=40 就要三亿多次调用，电脑会明显卡住。

**代码只有几行，不代表它跑得快。** 行数衡量的是"写起来省不省事"，不是"跑起来费不费劲"。

那怎么衡量？直接掐表计时吗？

---

## 二、为什么不能直接掐表

给一段代码计时，听起来最直接，但问题很多：

**第一，换台电脑结果就变。** 同一段代码，游戏本和办公本跑出来的秒数能差好几倍，这衡量的是电脑，不是算法。

**第二，同一台电脑每次也不一样。** 后台开着浏览器、杀毒软件在扫描、CPU 在降频，都会影响结果。跑十次能得到十个不同的数。

**第三，数据量小的时候看不出差别。** 排 10 个数，冒泡排序和快速排序都是"眨眼就完"，计时器甚至显示 0 毫秒，但数据量一大差距就是天壤之别。

**第四，代码还没写，没法先计时。** 面试官问你"这个思路的时间复杂度是多少"，你总不能说"等我回去写完跑一下再告诉你"。

> 💡 所以复杂度衡量的不是"跑了几秒"，而是"**数据量变大时，工作量按什么规律增长**"。它是算法的体检报告，不是秒表。

生活里也是这个道理。想知道两道菜谁做得快，不能各做一次掐表——灶火大小、刀工快慢、当天状态都不一样。更靠谱的办法是数步骤：一道菜 5 步，另一道 12 步，那后者天然更费时间。

---

## 三、算法效率的两个维度

算法效率分两方面看：

| | 时间复杂度 | 空间复杂度 |
|---|---|---|
| 衡量什么 | 运行速度 | 额外占用的空间 |
| 怎么算 | 基本操作的执行次数 | 额外变量的个数 |
| 关心程度 | 最核心 | 相对次要 |

**时间复杂度**：一个算法跑得快不快。严格说不是算秒数，而是算**基本操作执行了多少次**。一次赋值、一次比较、一次加法，都算一次基本操作。

**空间复杂度**：算法在运行过程中，除了输入数据本身，额外借用了多少空间。

早年间内存金贵，程序员会为了省几 KB 绞尽脑汁；现在内存大了，空间复杂度没那么要命，但绝不是不用管——递归开太深会把栈撑爆，缓存开太大也会拖垮程序。

> 💡 这两个东西经常互相换。哈希表用额外的空间换来了接近 O(1) 的查询速度；反过来，有些排序算法为了省空间，宁可多跑几趟。这就是常说的"**空间换时间**"和"**时间换空间**"。

## 四、大O表示法：只留最影响结果的那一项

### 4.1 先把次数数清楚

拿一个具体场景来数：学校礼堂要排座位、贴指示牌。

```java
public class Cx1 {
    static int seatPlan(int n) {
        int count = 0;

        // 每排 n 个座位，一共 n 排
        for (int row = 0; row < n; row++) {
            for (int col = 0; col < n; col++) {
                count++;
            }
        }

        // 三条走廊，每条挂 n 张路牌
        for (int i = 0; i < 3 * n; i++) {
            count++;
        }

        // 大门口固定 8 张总览海报
        int poster = 8;
        while (poster-- > 0) {
            count++;
        }

        return count;
    }

    public static void main(String[] args) {
        for (int n : new int[]{10, 100, 1000}) {
            System.out.println("n = " + n + "，一共 " + seatPlan(n) + " 次操作");
        }
    }
}
```

运行结果：

```
n = 10，一共 138 次操作
n = 100，一共 10308 次操作
n = 1000，一共 1003008 次操作
```

把次数写成式子：

```
座位     n × n   = n²
路牌     3n
海报     8

合计     F(n) = n² + 3n + 8
```

现在对比一下，n 变大时，各部分占多少：

```
n = 10      F(n) = 138        其中 n² = 100       低阶项占 27.54%
n = 100     F(n) = 10308      其中 n² = 10000     低阶项占  2.99%
n = 1000    F(n) = 1003008    其中 n² = 1000000   低阶项占  0.30%
```

n 越大，`3n + 8` 这点零头越不值一提。当 n 到一百万时，`3n + 8` 连零头的零头都算不上。

**这就是大O表示法的思路：不关心精确次数，只关心"增长的量级"。**

### 4.2 化简的三个步骤

课件里的规则可以归纳成三步：

1. **加法常数换成 1**——常数项不管多大，都记作 1
2. **只保留最高阶项**——低阶项在数据量变大后会被淹没
3. **去掉最高阶项的系数**——`3n²` 和 `n²` 是同一种增长趋势，系数不影响量级

拿刚才的式子走一遍：

```
F(n) = n² + 3n + 8
     ↓ 去掉低阶项 3n 和常数 8
     = n²
     ↓ 最高阶项系数是 1，不用动
     = n²
     ↓
     O(n²)
```

再练几个：

```
2n + 10          → 只留 2n     → 去掉系数 2   → O(n)
3n² + 5n + 7     → 只留 3n²    → 去掉系数 3   → O(n²)
100              → 常数        → 记作 1       → O(1)
n² + n + 1       → 只留 n²     → 系数为 1     → O(n²)
n³ + 100n²       → 只留 n³     → 系数为 1     → O(n³)
```

> **⚠️ 别把 O(1) 理解成"只执行一次"。** `O(1)` 的意思是**执行次数是固定的，不随数据量变化**。哪怕固定循环 100 次，只要 100 这个数字写死、跟输入无关，它就是 O(1)，不是 O(100)。

### 4.3 常见的几个阶

| 大O | 叫法 | 增长感受 | 生活里的对应 |
|---|---|---|---|
| `O(1)` | 常数阶 | 数据再多也不变 | 直接翻到书的第 5 页 |
| `O(logN)` | 对数阶 | 数据翻倍，只多一步 | 猜数字，每次排除一半 |
| `O(N)` | 线性阶 | 数据翻倍，工作量翻倍 | 一页页翻书找一句话 |
| `O(NlogN)` | 线性对数阶 | 比线性略快一点 | 高效排序（后面会讲） |
| `O(N²)` | 平方阶 | 数据翻 10 倍，工作量翻 100 倍 | 每个人都要和其他所有人握手 |
| `O(2^N)` | 指数阶 | 数据加 1，工作量翻倍 | 把所有组合都试一遍 |
| `O(N!)` | 阶乘阶 | 数据加 1，工作量翻好几倍 | 列出所有排列 |

从小到大排：

```
O(1) < O(logN) < O(N) < O(NlogN) < O(N²) < O(2^N) < O(N!)
```

数据量小的时候，这些差别不明显；数据量一上来，差距就是数量级的：

| 数据量 N | O(logN) | O(N) | O(NlogN) | O(N²) | O(2^N) |
|---|---|---|---|---|---|
| 10 | 4 | 10 | 33 | 100 | 1024 |
| 100 | 7 | 100 | 664 | 10,000 | 1.27×10^30 |
| 1000 | 10 | 1,000 | 9,966 | 1,000,000 | 约 10^301 |

表里的 `O(logN)` 取了向上取整，实际是 3.32、6.64、9.97 这样的值。

> 💡 这也是为什么算法题里，`O(N²)` 的写法在数据量到 10⁵ 时基本就过不了了——一亿次操作，再快的电脑也得等一会儿。

## 五、拿几个具体代码练手

### 5.1 只有一层循环：O(N)

奶茶店出杯，每杯两步：做一杯、贴一张标签；另外固定准备 10 个备用杯。

```java
public class Cx2 {
    static int makeTea(int n) {
        int count = 0;

        // 每杯奶茶两步：做一杯、贴一张标签
        for (int i = 0; i < 2 * n; i++) {
            count++;
        }

        // 另外固定准备 10 个备用杯
        int spare = 10;
        while (spare-- > 0) {
            count++;
        }

        return count;
    }

    public static void main(String[] args) {
        System.out.println("10 杯：" + makeTea(10) + " 次操作");
        System.out.println("100 杯：" + makeTea(100) + " 次操作");
    }
}
```

运行结果：

```
10 杯：30 次操作
100 杯：210 次操作
```

次数是 `2n + 10`。按三步法：留 `2n`，去系数，得到 **O(N)**。

杯数翻 10 倍，操作次数也差不多翻 10 倍——这就是线性增长。

### 5.2 有两个变量：O(M + N)

两个货架分别清点，A 架 M 件，B 架 N 件：

```java
public class Cx3 {
    static int stockTaking(int shelfA, int shelfB) {
        int count = 0;

        for (int i = 0; i < shelfA; i++) {
            count++;
        }

        for (int i = 0; i < shelfB; i++) {
            count++;
        }

        return count;
    }

    public static void main(String[] args) {
        System.out.println("A 架 30 件，B 架 70 件，共清点 " + stockTaking(30, 70) + " 次");
        System.out.println("A 架 300 件，B 架 70 件，共清点 " + stockTaking(300, 70) + " 次");
    }
}
```

运行结果：

```
A 架 30 件，B 架 70 件，共清点 100 次
A 架 300 件，B 架 70 件，共清点 370 次
```

这里有两个独立的规模，不能合并成一个 N，答案要写成 **O(M + N)**。

> **⚠️ 常见错误：** 看到两个循环就写 O(N²)。只有当两个循环的规模**都是同一个 N**、并且**嵌套**在一起时，才是 O(N²)。这里是并列的两个循环，规模还不一样，所以是 O(M + N)。

### 5.3 次数写死：O(1)

```java
public class Cx4 {
    static int checkLockers() {
        int count = 0;

        // 一共就 100 个柜子，这个数字是写死的，和任何输入都无关
        for (int i = 0; i < 100; i++) {
            count++;
        }

        return count;
    }

    public static void main(String[] args) {
        System.out.println("清点储物柜：" + checkLockers() + " 次");
        System.out.println("再来一遍：" + checkLockers() + " 次");
    }
}
```

运行结果：

```
清点储物柜：100 次
再来一遍：100 次
```

不管调用多少次、外面数据多大，这个方法内部永远是 100 次。常数阶，记作 **O(1)**。

### 5.4 双层循环：O(N²)

冒泡排序，顺手统计比较次数：

```java
import java.util.Arrays;

public class Cx5 {
    static int compares;

    static void bubbleSort(int[] arr) {
        for (int end = arr.length; end > 1; end--) {
            boolean sorted = true;

            for (int i = 0; i < end - 1; i++) {
                compares++;
                if (arr[i] > arr[i + 1]) {
                    int tmp = arr[i];
                    arr[i] = arr[i + 1];
                    arr[i + 1] = tmp;
                    sorted = false;
                }
            }

            if (sorted) {
                break;
            }
        }
    }

    public static void main(String[] args) {
        int[] reverse = {5, 4, 3, 2, 1};
        compares = 0;
        bubbleSort(reverse);
        System.out.println("逆序数组：" + Arrays.toString(reverse) + "，比较 " + compares + " 次");

        int[] ordered = {1, 2, 3, 4, 5};
        compares = 0;
        bubbleSort(ordered);
        System.out.println("有序数组：" + Arrays.toString(ordered) + "，比较 " + compares + " 次");
    }
}
```

运行结果：

```
逆序数组：[1, 2, 3, 4, 5]，比较 10 次
有序数组：[1, 2, 3, 4, 5]，比较 4 次
```

**最坏情况**是逆序，每一轮都要把相邻元素换个遍。5 个元素时：

```
第 1 轮：比较 4 次
第 2 轮：比较 3 次
第 3 轮：比较 2 次
第 4 轮：比较 1 次

合计：4 + 3 + 2 + 1 = 10 次
```

推广到 N 个元素：

```
(N-1) + (N-2) + ... + 1 = N(N-1)/2
```

去掉系数和低阶项，是 **O(N²)**。

**最好情况**是数组本来就有序，`sorted` 标记在第一轮结束时发现没换过，直接 `break`，只比较 N-1 次，也就是 **O(N)**。但这个最好情况带有偶然性，实际评估还是按最坏的 O(N²) 算。

> 💡 这段代码里加 `sorted` 标记是个很实用的优化：对已经有序的数组，它能从 O(N²) 降到 O(N)。但别指望它改变平均表现——大部分乱序数据还是逃不掉两层循环。

### 5.5 每次砍一半：O(logN)

猜数字游戏：1 到 1000 之间想一个数，每次猜中间，对方告诉你"大了"还是"小了"。

这就是二分查找：

```java
public class Cx6 {
    static int search(int[] arr, int target) {
        int left = 0;
        int right = arr.length - 1;
        int steps = 0;

        while (left <= right) {
            steps++;
            int mid = left + (right - left) / 2;

            if (arr[mid] == target) {
                return steps;
            } else if (arr[mid] < target) {
                left = mid + 1;
            } else {
                right = mid - 1;
            }
        }

        return -steps;
    }

    public static void main(String[] args) {
        int[] arr = new int[1000];
        for (int i = 0; i < arr.length; i++) {
            arr[i] = i + 1;
        }

        System.out.println("找 500：" + search(arr, 500) + " 步");
        System.out.println("找 777：" + search(arr, 777) + " 步");
        System.out.println("找 1：" + search(arr, 1) + " 步");
        System.out.println("找 1000：" + search(arr, 1000) + " 步");
    }
}
```

运行结果：

```
找 500：1 步
找 777：8 步
找 1：9 步
找 1000：10 步
```

1000 个数据，运气最好 1 步命中，运气最差 10 步也就找到了。

为什么是 10？因为每猜一次，剩下的范围就砍一半：

```
第 1 次后：最多剩 500 个
第 2 次后：最多剩 250 个
第 3 次后：最多剩 125 个
第 4 次后：最多剩  63 个
第 5 次后：最多剩  32 个
第 6 次后：最多剩  16 个
第 7 次后：最多剩   8 个
第 8 次后：最多剩   4 个
第 9 次后：最多剩   2 个
第 10 次后：最多剩  1 个
```

反过来看就是 `2^10 = 1024`，刚好覆盖 1000 个数据。所以最多需要 `log₂N` 次，记作 **O(logN)**。

> 💡 算法分析里的 `logN` 默认底数是 2，因为每次都砍一半；有些书写成 `lgN`，意思一样。底数是多少其实不影响量级，所以大O里干脆省略。

> **⚠️ 二分查找有个硬前提：数组必须是有序的。** 无序数组得先排序，而排序本身通常就要 O(NlogN)。如果只查一次，排完再二分未必比直接遍历快；只有在"排一次、查很多次"的场景里，二分才真正划算。

### 5.6 递归也不一定慢：O(N)

阶乘的递归写法：

```java
public class Cx7 {
    static int calls;

    static long factorial(int n) {
        calls++;
        if (n < 2) {
            return 1;
        }
        return n * factorial(n - 1);
    }

    public static void main(String[] args) {
        calls = 0;
        System.out.println("5! = " + factorial(5) + "，递归了 " + calls + " 次");

        calls = 0;
        System.out.println("10! = " + factorial(10) + "，递归了 " + calls + " 次");
    }
}
```

运行结果：

```
5! = 120，递归了 5 次
10! = 3628800，递归了 10 次
```

每层只做一次乘法，递归深度是 N，所以时间复杂度是 **O(N)**。

注意它和斐波那契的区别：阶乘每层只有**一个**递归调用，是一条线往下走；斐波那契每层有**两个**，会分叉成一棵树。这是两者复杂度差出天际的根本原因。

### 5.7 分叉的递归：O(2^N)

开头那段斐波那契，把调用次数数出来：

```
递归 fib(10) = 55，调用 177 次
递归 fib(20) = 6765，调用 21891 次
递归 fib(30) = 832040，调用 2692537 次
```

为什么会这么多？因为同一个子问题被反复算了很多遍。画一下 fib(5) 的调用过程：

```
                fib(5)
              /        \
          fib(4)       fib(3)
         /     \       /    \
     fib(3)  fib(2) fib(2) fib(1)
     /    \
 fib(2)  fib(1)
```

`fib(3)` 被算了两次，`fib(2)` 被算了三次。往下层数越多，重复越夸张，整棵树呈指数级膨胀。

严格说，它的调用次数是按 `1.618^n` 增长的（黄金比例），但大O里统一写成 **O(2^N)**——因为 `2^n` 是它的上界，量级同属指数级。

换个写法，用循环从前往后推：

```java
    static long fibFast(int n) {
        if (n < 2) {
            return n;
        }
        long a = 0;
        long b = 1;
        for (int i = 2; i <= n; i++) {
            long c = a + b;
            a = b;
            b = c;
        }
        return b;
    }
```

对比结果：

```
迭代 fib(30) = 832040，只循环 29 次
迭代 fib(50) = 12586269025，只循环 49 次
```

同样的结果，递归版 n=30 要两百六十多万次调用，循环版只要 29 次。这就是 **O(2^N)** 和 **O(N)** 的差距。

> 💡 这也解释了一个常见现象：有些题目用递归写看着优雅，一提交就超时。不是递归本身慢，而是**同一个子问题被重复计算**了。解决办法有两种：加缓存（记忆化搜索），或者直接改成循环（动态规划）。这两个词后面刷题会经常遇到。

## 六、最好、最坏和平均

同一段代码，输入不同，执行次数可能差很多。比如在一个长度为 N 的数组里找一个数：

| 情况 | 执行次数 | 说明 |
|---|---|---|
| 最好 | 1 次 | 第一个就是，纯属运气 |
| 最坏 | N 次 | 在最后一个，或者根本没找到 |
| 平均 | 约 (N+1)/2 次 | 每个位置被找到的概率相同 |

这三种都有人关心，但**实际评估一般看最坏**：最坏情况是算法给出的承诺，用户可不管你今天运气好不好。

> 💡 也有例外。快速排序的最坏是 O(N²)，平均是 O(NlogN)，实际用起来几乎总是接近平均，所以大家照样用它。看复杂度时要知道自己在看哪一种。

## 七、空间复杂度

空间复杂度衡量的是算法运行过程中**临时占用的空间**，算法输入的原始数据不算在内。

它不是算"占了多少字节"，而是算**额外开了多少个变量、多少个数组元素、多少层栈帧**，同样用大O表示。

### 7.1 只用几个变量：O(1)

还是刚才的冒泡排序。整个过程中新开的变量只有：`end`、`sorted`、`i`、`tmp`，再加一个计数器 `compares`。

不管数组有 10 个元素还是 100 万个元素，这几个变量就这么多，不会跟着涨。所以空间复杂度是 **O(1)**。

> 💡 这种"只借常数个额外变量"的算法，叫**原地**操作。冒泡、插入、选择排序都是原地的。

### 7.2 开了和 N 一样大的数组：O(N)

如果要生成斐波那契数列的前 n 项并存起来：

```java
static long[] fibonacci(int n) {
    long[] result = new long[n + 1];
    result[0] = 0;
    result[1] = 1;
    for (int i = 2; i <= n; i++) {
        result[i] = result[i - 1] + result[i - 2];
    }
    return result;
}
```

这里 `new long[n + 1]` 开了 n+1 个格子，n 越大占得越多，空间复杂度是 **O(N)**。

注意区分：**输入不算，额外开的才算**。如果方法接收一个长度为 N 的数组、只做原地修改，那额外空间还是 O(1)。

### 7.3 递归的栈帧：O(N)

阶乘递归每往下走一层，就有一个调用没返回，JVM 得给它留一个栈帧，存参数、返回地址、临时变量。

n=5 时有 5 层栈帧叠着，n=100000 时有 10 万层：

```
factorial(5)
└─ factorial(4)
   └─ factorial(3)
      └─ factorial(2)
         └─ factorial(1)   ← 到这儿才开始往上返回
```

每层栈帧占的空间是固定的，层数是 N，所以空间复杂度是 **O(N)**。

> **⚠️ 递归不是"不占空间"，只是把空间从堆挪到了栈。** 栈的容量有限，递归太深会抛 `StackOverflowError`，而且这个错误没法用 try-catch 兜住。

三种情况放一起对比：

| 算法 | 额外空间 | 为什么 |
|---|---|---|
| 冒泡排序 | O(1) | 只用了几个临时变量 |
| 生成斐波那契数组 | O(N) | 开了长度为 n+1 的数组 |
| 阶乘递归 | O(N) | 递归 N 层，压了 N 个栈帧 |

## 八、复杂度该怎么用起来

看一段代码估复杂度，可以按这个顺序走：

1. **先找循环和递归**——它们才是工作量的主要来源，赋值、判断这些零散语句最多算常数
2. **看循环是并列还是嵌套**——并列相加，嵌套相乘
3. **看循环变量怎么变**——每次加 1 是 O(N)，每次乘 2 或除以 2 是 O(logN)
4. **化简**——去常数、留最高阶、去系数

举几个常见的判断：

```
一层 for，循环 N 次                  → O(N)
两层 for，都循环 N 次（嵌套）          → O(N²)
两层 for，各自循环 N 次（并列）        → O(N)
for 里每次 i *= 2                    → O(logN)
递归，每层只调自己一次                → O(递归深度)
递归，每层调自己两次                  → O(2^深度)
```

这套判断方法，在后面每个容器都会用到。先剧透几个结论，到时候会逐个验证：

| 操作 | `ArrayList` | `LinkedList` | `HashMap` |
|---|---|---|---|
| 按下标取 | O(1) | O(N) | —— |
| 头部插入 | O(N) | O(1) | —— |
| 按 key 查 | —— | —— | 平均 O(1) |
| 是否包含某元素 | O(N) | O(N) | 平均 O(1) |

> 💡 这也是上一篇说"选错容器可能慢几十倍"的原因：同样是"查一个元素在不在"，`ArrayList` 要逐个比，`HashMap` 直接算位置。数据量一大，O(N) 和 O(1) 就是两个世界。

## 总结

这一篇的核心就三件事：**怎么数、怎么化简、怎么比**。

**时间复杂度的算法：**
- 数基本操作的执行次数，写成关于数据规模 N 的函数
- 只跟一个变量有关就写 N，有两个独立规模就写 M+N
- 循环嵌套相乘，循环并列相加
- 每次砍一半的循环，是 O(logN)

**大O化简三步：**
1. 加法常数记作 1
2. 只保留最高阶项
3. 去掉最高阶项的系数

**常见阶从小到大：**
```
O(1) < O(logN) < O(N) < O(NlogN) < O(N²) < O(2^N) < O(N!)
```

**几个容易踩的点：**
- `O(1)` 不是"只执行一次"，是"次数固定、不随数据规模变化"
- 两个并列循环不等于 O(N²)，得看规模和是否嵌套
- 最好情况和最坏情况可能差很远，评估一般看最坏
- 递归的时间看"每层分几个叉"，空间看"递归有多深"
- 二分查找的 O(logN) 有个前提：数据必须有序

**空间复杂度：**
- 算的是额外空间，输入数据不算
- 只看变量个数、数组长度、栈帧层数，不看字节数
- 递归深度为 N，空间就是 O(N)，太深会栈溢出

下一篇换个轻松点的话题——包装类和泛型。这两个东西平时写代码天天在用，但很多人说不清 `int` 和 `Integer` 到底差在哪、`ArrayList<Integer>` 后面那对尖括号到底在干什么。把这两块理清楚，后面手写 `ArrayList` 和 `HashMap` 才不会卡壳。
